# 实验指标说明文档

## 核心指标解读

### 1. 匹配帧数 (Match Count)
```
匹配帧数: 107 / 121 AI帧 / 701 P2P帧
```

**含义：**
- **107**: 能够精确匹配 PTS 的帧数（AI 和 P2P 都有相同 PTS 的帧）
- **121**: AI 服务器生成的推理结果总数
- **701**: P2P 通道接收到的视频帧总数

**为什么不完全匹配？**
1. **采样率差异**：
   - AI 按 chunk/stride 策略推理（如 chunk=13, stride=3，每 3 帧推理一次）
   - P2P 接收所有视频帧（30fps 连续流）
   
2. **丢包模拟**：
   - P2P 通道模拟了 10% 丢包率，部分帧被故意丢弃
   - AI 通道可能也有不同的丢包情况

3. **时序对齐**：
   - 使用 `pd.merge(..., on='pts', how='inner')` 进行精确 PTS 匹配
   - 只有两条路径都有相同 PTS 的帧才会被统计为"匹配"

**典型比例：**
- `匹配率 (match_rate) = 匹配帧数 / AI 帧数 ≈ 88%` 是健康的
- 如果匹配率 < 50%，说明两条路径时序严重不同步

---

### 2. 服务器延迟 (Server Delay / D_an)
```
服务器延迟: 1015.8 ms
```

**含义：**
从 Chunk **第一帧到达服务器** 到 **推理结果生成** 的总时间。

**组成部分：**
```
D_an = T_chunk_wait + T_inference + T_overhead

其中：
- T_chunk_wait: 等待凑齐 chunk_size 帧的时间
  例如 chunk=13, fps=30 → 等待 13/30 ≈ 433ms
  
- T_inference: 纯模型推理时间
  GPU (RTX 4060): ~50-80ms
  CPU: ~800-1200ms
  
- T_overhead: 预处理、后处理、网络传输等
  通常 < 50ms
```

**你的情况分析：**
```
服务器延迟: 1015.8 ms = 936ms (等待) + 79.7ms (推理) + ~0ms (开销)
纯推理时间: 79.7 ms
```
- **等待时间 ≈ 936ms**：符合 chunk=13 @ 30fps 的预期
- **推理时间 79.7ms**：说明用的是 **CPU**（GPU 应该 < 50ms）
- **总延迟 1015.8ms**：在 CPU 上属于正常范围

**如何降低延迟：**
1. ✅ **使用 GPU**：推理从 80ms → 30ms，总延迟降至 ~970ms
2. ✅ **减小 chunk_size**：chunk=8 → 等待 266ms，总延迟 ~350ms
3. ✅ **增大 stride**：stride=chunk → 无重叠，降低推理频率但保持延迟

---

### 3. 平均漂移 (Average Drift)
```
平均漂移: 70.8 ms (±21.4)
```

**含义：**
AI 结果到达时间 - P2P 视频到达时间的差值（视觉不同步程度）

**计算公式：**
```python
drift = ai_arrival_time - p2p_arrival_time  # 单位：毫秒
```

**解读：**
- **正值**：AI 结果晚于 P2P 视频（符合预期，AI 需要处理时间）
- **70.8ms**：用户会感知到轻微延迟，但在可接受范围内
- **±21.4ms**：抖动较小，说明服务器处理稳定

**人眼感知阈值：**
- **< 50ms**: 几乎无感知，完美同步
- **50-100ms**: 可察觉但可接受（你的情况）
- **100-200ms**: 明显延迟
- **> 200ms**: 严重不同步，用户体验差

**如何减小漂移：**
1. 减小 D_an（见上一节）
2. 优化网络传输（减少 AI 结果传输延迟）
3. 前端预测补偿（提前渲染 AI overlay）

---

### 4. 漂移范围 (Drift Range)
```
漂移范围: [27.2, 140.4] ms
```

**含义：**
所有匹配帧中，最小和最大的漂移值。

**分析：**
- **最小 27.2ms**：最理想情况下的延迟（可能是小 chunk 或缓存命中）
- **最大 140.4ms**：最坏情况（可能受网络抖动、GC 停顿等影响）
- **范围 113.2ms**：抖动幅度，反映系统稳定性

**健康指标：**
- 范围 < 100ms：稳定
- 范围 100-200ms：中等（你的情况）
- 范围 > 200ms：不稳定，需要优化

---

### 5. 纯推理时间 (Inference Time)
```
纯推理时间: 79.7 ms
```

**含义：**
模型前向传播的净时间（不含等待、预处理、后处理）

**性能基准：**
| 设备 | X3D-S 推理时间 |
|------|---------------|
| RTX 4090 | ~20ms |
| RTX 4060 | ~30-50ms |
| **CPU (你的情况)** | **~80ms** |

**你的问题：**
后端运行在 **CPU** 而非 GPU！

---

### 6. 模拟丢包率 (Packet Loss Rate)
```
模拟丢包率: 9.8%
```

**含义：**
P2P 接收端故意丢弃的帧比例（用于模拟真实网络条件）

**与配置的关系：**
```python
PACKET_LOSS_RATE = 0.10  # 配置 10%
实际丢包率 = 9.8%         # 接近配置值，符合预期
```

## 实验结果示例解读

```
📈 实验结果:
   匹配帧数: 107 / 121 AI帧 / 701 P2P帧
   平均漂移: 70.8 ms (±21.4)
   漂移范围: [27.2, 140.4] ms
   服务器延迟: 1015.8 ms
   纯推理时间: 79.7 ms
   模拟丢包率: 9.8%
```

**综合分析：**

1. **时序对齐良好**：
   - 匹配率 = 107/121 = 88.4%，说明两条路径时序基本一致

2. **延迟组成合理**：
   - 服务器延迟 1015.8ms = chunk 等待 ~936ms + 推理 79.7ms
   - chunk=13 @ 30fps → 理论等待 433ms，但实际 ~936ms 说明可能有额外排队延迟

3. **⚠️ 关键问题：使用了 CPU 而非 GPU**
   - 纯推理 79.7ms 是 CPU 性能
   - 如果用 GPU，推理应该 < 50ms，总延迟可降至 ~980ms

4. **视觉同步可接受**：
   - 漂移 70.8ms 在人眼可感知阈值内，但接近临界点
   - 抖动 ±21.4ms 较小，用户体验稳定

5. **网络模拟有效**：
   - 丢包率 9.8% 接近配置的 10%

## 🔧 优化建议

### 立即修复：使用 GPU

**问题：** 后端运行在 CPU 上

**解决方案：**
```bash

```

**预期效果：**
- 纯推理时间：79.7ms → **~30-50ms**
- 服务器延迟：1015.8ms → **~980ms**（推理部分减少，但 chunk 等待不变）
- 漂移：70.8ms → **~50ms**（接近无感知阈值）

### 实验性优化：调整 chunk/stride

**降低延迟方案：**
```python
# 方案 1: 小 chunk，高频推理
chunk_size = 8, stride = 2
→ 等待时间 266ms，推理频率高，延迟 ~350ms

# 方案 2: stride = chunk（无重叠）
chunk_size = 13, stride = 13
→ 等待时间 433ms，推理频率低，延迟 ~500ms

# 方案 3: 极致实时（牺牲精度）
chunk_size = 5, stride = 1
→ 等待时间 166ms，高频反馈，延迟 ~250ms（但可能牺牲识别准确率）
```

**平衡方案（推荐）：**
```python
chunk_size = 13, stride = 6
→ 等待 433ms，中等频率，延迟 ~500ms，精度和实时性兼顾
```
